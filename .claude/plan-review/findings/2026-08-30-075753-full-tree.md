# Plan review — full tree — post-decision consistency pass

Reviewed: all 43 documents under `plan/`, the template/index, decision log, glossary, milestone map,
review tooling, and the prior 2026-08-29 findings.

Verdict: **not ready for implementation**. The corpus is unusually thorough and its mechanical
structure is strong, but recently accepted decisions `D-19`–`D-21` were not propagated, several
milestone contracts contradict their owning documents, and critical M1/M2 choices remain open.

Mechanical check before this review: 43 documents, 43 index rows, all 35 requirements claimed, 96
declared open questions, links/dependencies/ownership clean. The enhanced check now also exposes
unknown requirement references and closed questions retained as active questions.

## Blocking findings (10)

### F-1 · `D-19` vs `02`, `22`, `23`, `24` · exchanger modes contradict the binding decision

**Evidence.** `D-19` defines three modes and says secondary properties promote an exchanger to Rated
mode (`06-decision-log.md:565-586`). `22` still selects only Duty/ Rated by whether side 2 is connected
(`22-component-model.md:236-244`); `23` lists only duty and rated flow groups
(`23-topology-and-graph.md:138-139`); `24` says an unconnected rated exchanger is an error and makes
topology the switch (`24-auto-sizing.md:339,440-441`); the glossary repeats the obsolete topology-only
definition (`02-glossary.md:104`).

**Impact.** `HX1 ... in2=85 out2=45 u=3300` is valid Rated mode under the decision and invalid or inert
under the component/sizing specifications. Implementers cannot write the binder, graph, diagnostics,
or acceptance tests consistently.

**Fix.** Add a normative three-mode table to `22`, use "extended" for Rated+Coupled, define each
mode's ports/equations/error cases, then update `23`, `24`, `02`, `15`, diagnostics, and reference
examples from that owner.

### F-2 · `D-20` exists only in the decision log · symbol ownership and contracts are contradictory

**Evidence.** `D-20` requires `IComponent.SymbolId`, an `IComponent`/`IFlowComponent`/`IObserver`
hierarchy, Core-owned `SymbolDefinition`, and symbol metadata (`06-decision-log.md:612-647`). The
actual `IComponent` has none of these (`22-component-model.md:34-73`); `53` still owns a frontend
"symbol library" (`53-canvas-renderer.md:6,24,112`); `42` metadata omits symbol definitions
(`42-rest-contract.md:88-96`); `26` has no symbol field; and `03` still records the geometry question
that `D-20` says it closed (`03-repository-layout.md:224-229`).

**Impact.** Core, API, frontend, and exporter implementations will choose incompatible symbol
sources. The decision log is binding, so following the subsystem documents produces code that
violates the plan.

**Fix.** Decide which document owns the declarative symbol schema, propagate its wire shape and
fallback behavior, change `53` from owning symbols to consuming them, and close the obsolete question.

### F-3 · `D-21` is untraceable and unimplemented in the specification

**Evidence.** `D-21` adds a `sensor` observer kind and `FS2113` (`06-decision-log.md:678-711`) but
references nonexistent requirement `R-36`; `D-20` similarly references nonexistent `R-37`
(`06-decision-log.md:670,711`). No sensor exists in `01`'s requirement register, `22`'s component
contract, `15`'s registry, `26`'s model shape, `34`'s controller contract, or `53`'s symbols.

**Impact.** The decision silently creates another component and public language surface while `R-09`
still promises five kinds. A controller may measure `N2.t` directly under `34`, or be required to use
a sensor under `D-21`; both readings are reasonable.

**Fix.** Prefer deferring persistent sensors until a user-visible instrumentation requirement exists.
If retained, add the missing requirement, milestone, component/semantic/model/API/render contracts,
diagnostic entry, documentation page, and a precise rule for whether controllers require sensors.

### F-4 · M4 requires both cancellation and non-cancellation on edit

**Evidence.** The M4 exit criterion says editing during a run cancels it
(`05-milestones-and-acceptance.md:179`). API architecture says an edit explicitly does not cancel a
transient (`41-api-architecture.md:111-114`), and frontend architecture implements that behavior
(`51-frontend-architecture.md:136-140`).

**Impact.** One correct implementation necessarily fails another correct acceptance test.

**Fix.** Keep explicit cancellation: edits update analysis, preserve the running snapshot, show
"script changed", and require Stop/Run to restart. Replace the milestone criterion accordingly.

### F-5 · syntax-reference inference count and narrative are wrong in four authorities

**Evidence.** The syntax script connects all three `3WV` ports: `HE1-3WV`, `3WV-N2`, `3WV-N3`.
Therefore I3 fires only for unconnected pump ports (2), not for `3WV`. Correct inference is I1=3,
I2=1, I3=2: **six** `FS1510`, not seven. The incorrect seven is normative in
`01-vision-and-scope.md:179-188`, repeated in `42-rest-contract.md:137-159`,
`56-console-log.md:173-178`, and `16-diagnostics.md:252-257`.

The same section says `N3` "is an open port" (`01:164`), although it is an I1-inferred terminal node,
and claims the script produces a sized pump/valve/pipework (`01:168-170`) immediately before stating
that it is unsolvable and has an unconnected pump (`01:174-177`).

**Impact.** Parser/binder acceptance tests and API/UI golden examples encode impossible results.

**Fix.** Recompute the inventory once in `01`, make other documents cite it, correct the comment and
product-promise prose, and add a mechanical fixture that derives counts from the eventual sample.

### F-6 · `FS4008` is simultaneously live in M2 and reserved for M6

**Evidence.** M2 requires `FS4008` (`05:132`), and `22` says it is live (`22:364`). The diagnostic
registry says it is reserved, not emitted until M6, because the exchanger is one-sided
(`16-diagnostics.md:98`).

**Impact.** A correct M2 component cannot satisfy the M1 diagnostic contract and milestone at once.

**Fix.** Update `16` for `D-17`/`D-19`: M2, Rated/Coupled modes, normative threshold source, and
component association.

### F-7 · M2's pump and pipe behavior is intentionally undecided

**Evidence.** `22` calls the bare-connection question its highest-priority open question and says it
blocks the pump sizing basis and M2 demo (`22-component-model.md:631-639`); `23` calls it the highest
priority in the tree (`23-topology-and-graph.md:530-541`).

**Impact.** The flagship terse syntax has no defined pressure loss when no pipe is declared, so a bare
`pump` cannot be sized. This is a missing core contract, not harmless future detail.

**Fix.** Adopt the honest rule already implied by the solvable reference circuits: bare connections
are ideal links; pressure loss requires an explicit pipe (or other resistance). State that the syntax
reference is not a sizing example. Do not invent a default length.

### F-8 · milestone tolerances and the accuracy claim are not defined

**Evidence.** `05` uses "within tolerance" repeatedly and explicitly says this blocks M2 exit
(`05:242-246`). `01` leaves the system's accuracy claim open (`01:533-536`). `14` also lacks the
fixed-point tolerance that triggers `FS1405` (`14:305-308`).

**Impact.** Acceptance cannot distinguish a correct solver from a plausible one, and users cannot know
the validation envelope.

**Fix.** Add one normative verification matrix: quantity, reference case/source, absolute+relative
tolerance, valid domain, and rationale. Cite it from milestones, diagnostics, and docs.

### F-9 · pressure semantics and absolute-temperature syntax remain undecided M1 contracts

**Evidence.** Gauge vs absolute pressure blocks the substance boundary and every pressure diagnostic
(`13-type-and-unit-system.md:369-376`). The meaning of `K` in a context-free binding blocks the unit
system invariant (`13:377-383`).

**Impact.** These choices affect AST typing, stored values, property calls, diagnostics, wire values,
and every pressure/temperature example. Retrofitting either after M1 is a breaking language change.

**Fix.** Decide before M1: recommended gauge in script/UI with explicit atmospheric-reference
configuration and absolute at the property boundary; use distinct, context-free syntax for absolute
temperature versus deltas rather than backward inference.

### F-10 · external property and validation sources are not verified

**Evidence.** The SharpProp API and packaging are explicitly unverified and block the adapter design
(`21-fluid-and-state.md:318-322`); its thread safety blocks DI lifetime (`41:226-229`). The testing
strategy says reference values for property validation are unresolved and that this is its
highest-priority question (`62-testing-strategy.md:312-317`).

**Impact.** Public interfaces, concurrency, CI, and the central accuracy gate are based on assumed
external behavior. The plan correctly labels the uncertainty but has not scheduled the prerequisite.

**Fix.** Make a time-boxed M0 spike a hard dependency of M1/M2: compile a minimal adapter, exercise
each call, test concurrent calls, record package/native deployment behavior, and freeze independent
reference datasets with provenance.

## Should-fix findings (10)

### F-11 · requirement-to-milestone traceability is incomplete

`05` requires every requirement to appear in milestone criteria or be explicitly deferred (`05:236-238`),
but 16 of 35 IDs do not appear there: `R-03`, `R-04`, `R-07`, `R-08`, `R-10`, `R-13`, `R-14`,
`R-16`, `R-18`, `R-20`, `R-27`, `R-29`, `R-30`, `R-32`, `R-33`, `R-34`. Add a compact requirement ×
milestone matrix; frontmatter ownership alone does not establish delivery.

### F-12 · open-question hygiene obscures readiness

There are 96 declared questions; seven are struck through as Closed but still count as active (`22`,
`23`, `27`, `33`, `34`, `36`, `71`). Other questions explicitly say they block current acceptance,
while deferred product ideas sit in the same flat structure. Remove closed entries, move deferred
items to `72`, and classify the remainder as decide-now, spike, or decide-by-milestone.

### F-13 · review state does not describe the current tree

`.claude/plan-review/state.json` ends at the 2026-08-29 pass, while `plan/README.md:31-39` describes a
2026-08-30 pass and six later decisions. Make report/state updates atomic; do not treat document
`status` as review history.

### F-14 · "Phase 1" is undefined and conflicts with M1

The tree uses "Phase 1" or "Phase-1" 42 times to mean roughly the first release, while the formal
phase table names `M1` as language-only. Thus "five Phase-1 components" can mean components in a
milestone that expressly has no physics. Define `v1 scope` (for M0-M5) and use exact milestones (`M1`,
`M2`, etc.) everywhere else.

### F-15 · the glossary is stale after the new decisions

Besides the obsolete two-mode definition (`02:104`), the glossary lacks `Coupled mode`, `Observer`,
`Sensor`, `SymbolId`, and `SymbolDefinition`. Update it only after F-1/F-3 settle, so it reflects one
normative model.

### F-16 · file open/save is deferred past the point the product is usable

The editor explicitly has no save and binds `Ctrl+S` to Solve (`52-editor.md:246-258`); the roadmap
waits until "the second script anyone writes" (`72-roadmap.md:82`). That trigger is guaranteed on the
first real use. Promote browser file open/download-save into M3; keep server persistence and multi-file
projects deferred.

### F-17 · compatibility and migration lack a release contract

Pre-1.0 versioning is open (`63:249-254`), the script has no declared language version/migration
policy, and model/API versioning is separate. Specify supported version windows, breaking-change
diagnostics, catalogue pinning, and whether old scripts are migrated, rejected, or interpreted under
their original version.

### F-18 · non-functional requirements are scattered instead of owned

The plan mentions 200 components, 10 fps, a 300 ms debounce, unknown script-size limits, platform
packaging, and accessibility fragments, but no root quality-attribute budget owns them. Add a small
table for supported browsers/OS, model size, latency, transient throughput, memory,
determinism/reproducibility, accessibility, and local-vs-hosted security assumptions.

### F-19 · air-side scope is contradictory

`01` says an air circuit needs fan and coil kinds and leaves R-08's milestone undecided (`01:529-532`),
while `15` says `fan` aliases to `pump` and the first release models it with pump equations
(`15:155-166`). Decide whether M2 supports only humid-air property calls or a valid air circuit. Do
not call psychrometrics "first-class" if no reference air circuit can run.

### F-20 · mutable diagnostics are duplicated on the wire

`42` returns diagnostics both inside `model` and in a top-level duplicate (`42:43-48`). This creates
two arrays that may disagree. Return one canonical collection; consumers needing only diagnostics
already have `/validate`.

## Essential missing contracts

1. File/project lifecycle: open, save/download, dirty state, recovery, and naming.
2. Script-language compatibility and migration across releases and catalogue versions.
3. A root non-functional/operational envelope with measurable scale and latency budgets.
4. A verified external-property adapter and independent validation datasets.
5. A declared engineering accuracy envelope, including the effect of omitted fittings/minor losses.
6. A precise supported-domain statement: hydronic only for v1, or a runnable air-side reference model.
7. Accessibility/keyboard operation for canvas selection, hover-equivalent state access, warnings,
   theme/contrast, and motion reduction.

## Recommended phasing

1. **M0 — risk retirement:** SharpProp/package/thread-safety spike; freeze reference datasets; decide
   pressure and temperature syntax; settle file/versioning baseline.
2. **M1 — language spine:** implement only grammar needed through M3, with future schedule/controller
   productions only when semantics are fixed. Correct the syntax reference.
3. **M2a — hydraulic vertical slice:** explicit pipes, ideal bare links, water, flow components,
   graph, sizing, Newton, simple/cooling loops, accuracy matrix.
4. **M2b — coupled thermal slice:** D-19's Rated/Coupled exchanger, second hydraulic component,
   substation, catalogue geometry.
5. **M3 — usable product:** REST/editor/canvas, declarative symbols, docs, file open/save, static SVG/PNG.
6. **M4 — transient/control:** immutable run snapshot, explicit cancellation, PI first, streaming
   diagnostic lifetime and playback retention settled before implementation.
7. **M5 — write-back:** canvas edits only after persistence/versioning makes source mutation safe.
8. **M6 — evidence-driven:** subsystems, evolutionary sizing, DXF/JSON distribution; decide from usage.
