### F-1 · `22`, `32`, `33` · feasibility — DN used as a bore inside worked examples

**Finding.** `22-component-model`'s pipe table declares `dn` as `Dimension = Length`, canonical `mm`,
range 6…2000 — contradicting `02-glossary` ("Nominal diameter **designation**, dimensionless … **DN is
not a length**") and `CLAUDE.md`. Three worked examples then use the DN number as a diameter:

| Doc | Says | With the 27.3 mm EN 10255 bore |
|---|---|---|
| `32` worked example | 0.575 kg/s in DN25 → "v = 1.18 m/s" | **0.98 m/s** (1.18 needs d = 25.0 mm) |
| `33` worked example | "5 m of DN25 = 2.45 l", τ = 10.2 s, CFL 9.2 s | **2.93 l**, τ = **12.2 s**, CFL **11.0 s** |
| `24` worked example | DN25 velocity 0.44 m/s | **0.41 m/s** (as `27` correctly states) |

**Why it blocks.** `dn` typed as a `Length` in mm means a sizer reading `dn=25` computes area from
25 mm: a 16 % area error and roughly a factor of two in pressure gradient, exactly the consequence the
glossary warns about. The examples then bake the wrong numbers into acceptance criteria.

**Suggested fix.** Give `dn` its own dimensionless `NominalDiameter` kind per the glossary; make the
catalogue's `InsideDiameter` the only thing hydraulics may read. Recompute `32`'s velocity, `33`'s
segment volume / residence time / CFL limit, and `24`'s velocity from the catalogue ID.

### F-4 · `22` · feasibility — the pump affinity law is mis-parenthesised

**Finding.** `H(ṁ, n) = n²H₀ − k(ṁ/n)²`. The affinity laws give
`H(Q,n) = n²·[H₀ − k(Q/n)²] = n²H₀ − k·ṁ²`. The `n²` must distribute over both terms. As written the
loss term carries an extra `1/n²`: at n = 0.5 it is 4× too large.

**Why it blocks.** M4 has variable-speed pumps and a PI controller acting on speed, so n ≠ 1 is the
normal case, and the error is silent at n = 1 where every test will be written. It also divides by n,
so the residual is undefined at n = 0 — violating `22`'s own invariant 7 (continuous and differentiable
over the search domain). The correct form is finite at n = 0 and correctly models a stopped pump as a
pure resistance.

**Suggested fix.** `H(ṁ, n) = n²·H₀ − k·ṁ²`, and add a test at n = 0.5 and n = 0.

### F-5 · `36` + `22` · feasibility — the valve regularisation is C⁰, not C¹

**Finding.** `36` specifies `Q = Kv·Δp / √(Δp_reg·ρ_r)` below the threshold and asserts it is
"C¹-continuous at the join"; `22` says "matched in value and slope". A line **through the origin** that
matches `C√Δp` in value at `Δp = a` has slope `C/√a`, while the √-law's slope there is `C/(2√a)` —
exactly 2× off. Value and slope cannot both be matched by a line through the origin.

**Why it blocks.** `36` invariant 4, `22` invariant 7, and two acceptance criteria ("The valve law is
C¹ at 100 Pa, verified by finite differences either side") all assert a property the stated formula does
not have. An implementer follows the formula, the finite-difference test fails, and the apparent fix —
loosening the test — removes the guard that Newton needs.

**Suggested fix.** A quadratic through the origin matching both conditions works and stays monotone:
`Q = (3C/2√a)·Δp − (C/2a^1.5)·Δp²` for `0 ≤ Δp < a`, with `C = Kv/√ρ_r`, extended oddly via `sign(Δp)`.
(Check: `Q(a) = C√a`, `Q'(a) = C/(2√a)`, `Q(0) = 0`, `Q' > 0` throughout.)

### F-6 · `23` · completeness — the well-posedness count is a tautology and omits every constraint

**Finding.** Unknowns = 2N + B. Equations = N (mass) + B (Δp) + N (energy) + 1 (reference) − 1
(redundant mass) = 2N + B. These are **identically equal for any N and B**, so the counting check can
never detect an imbalance, and `FS2210` / `FS2211` (over- / under-specified) are unreachable from it.

The table also omits every source of real imbalance: stated node boundary conditions (`t`, `p`, `flow`),
and component constraints — `HE1 power=30 in=20 out=50` is three constraints, while `22` says the
component "contributes one equation and zero unknowns". Nothing in the tree says where the other two
land.

**Why it blocks.** `23` exists to catch topology errors before the solver, and this is its mechanism.
It also means `31`'s "15 unknowns and 15 equations" acceptance criterion is checking nothing.

**Suggested fix.** Make the count boundary-aware:
unknowns = 2N + B + component-owned unknowns (valve position, pump head when sized);
equations = (N−1) mass + B pressure-drop + N energy + Σ stated boundary conditions + Σ component
constraint equations + 1 datum. Then work the count through the canonical script (F-7) and show a
deliberately over-specified variant producing `FS2210`.

### F-9 · `12` + `13` · contract precision — `unit-symbol` is undefined and compound units collide with operators

**Finding.** `12-grammar`'s lexical grammar contains `quantity = number , [whitespace] , unit-symbol`
and **never defines `unit-symbol`**. `13`'s symbol table lists compound symbols (`kg/s`, `m3/h`,
`l/min`), its dimension table uses `kJ/(kg·K)`, and `14`'s worked example writes `4.18 kJ/(kg*K)`.
`/`, `(`, `*` and `)` are all expression tokens, and `12`'s word-classification rule 3 matches only
`number , unit-symbol` **within one word** — it cannot reach past a `/`.

So `let cp = 4.18 kJ/(kg*K)` is ambiguous between one quantity literal and
`(4.18 kJ) / (kg * K)` with `kg` and `K` as identifiers, and `14`'s own worked example depends on the
first reading.

**Why it blocks.** The lexer cannot be written from this. It is also the highest-consequence ambiguity
in the tree: the two readings differ by a factor of 4180.

**Suggested fix.** Define `unit-symbol` explicitly in `12` as a maximal-munch match against `13`'s
table with compound symbols as **atomic entries** (longest-first), listing every accepted spelling; and
settle one spelling in `13` (`kJ/(kg*K)` — `·` is not typeable). Add a test that `Q / (cp * dT)` and
`4.18 kJ/(kg*K)` lex differently and state which token sequence each produces.

### F-10 · `13` + `14` · contract precision — no dimensional algebra for `*` and `/`

**Finding.** `13` calls the dimension set "closed" and gives combination rules only for temperature and
pressure. `14` defines `*`, `/`, `%` with **no rule for the resulting dimension**, yet its own worked
example requires Power ÷ (SpecificHeat × TemperatureDelta) → MassFlow. `FS1305` ("Cannot {op} a {a} and
a {b}") implies some combinations are rejected, but nothing says which. `Q / dT` (W/K) is not in the
closed set at all, and the spec is silent on what happens.

**Why it blocks.** The evaluator's central type rule is missing. Two implementers will pick differently:
one rejects everything not in the enum (breaking `14`'s example), one allows everything (losing the
dimension safety `13` exists for).

**Suggested fix.** State that a `Quantity` carries an **exponent vector over SI base dimensions**
internally; `*` and `/` combine the vectors; the named `Dimension` enum is a *label* looked up from the
vector. An unnamed intermediate is legal inside an expression; assigning one to a parameter that expects
a named dimension is `FS1304`, and `FS1305` is reserved for genuinely illegal operations (adding
mismatched vectors). This preserves `Temperature`/`TemperatureDelta` as special-cased affine types.

## 🟡 Should fix (18)

### F-11 · `14` · feasibility — the deferred-expression fixed point has no non-zero solution as posed

`PU1 pump head=1.2*HE1.dp` in a closed loop. At equilibrium the pump head **equals** the total loop
drop, and every passive drop scales as ṁ², so `dp_HE1 = φ·H` with φ ≈ constant. From the document's own
iteration 1 (H = 42 kPa, dp = 18.0 kPa), φ = 0.429, and the map is `H ← 1.2·φ·H = 0.514·H` — geometric
collapse to **zero flow**, not convergence to 2.08 m:

```
42.0 → 21.6 → 11.1 → 5.7 → 2.9 → 1.5 → …
```

The table instead shows dp nearly constant (18.0 → 17.1 → 17.0) while H halves, which needs
∂ln dp/∂ln H ≈ 0.07 against ≈ 1.0 for turbulent flow. The claim that the iteration is "strongly
contracting, since raising the head barely changes the drop" is backwards for a closed hydronic loop.
If instead the flow is pinned by the HX duty (`power` + `in` + `out`), dp is *exactly* constant, the
map converges in one step, and the pump head no longer equals the loop drop — i.e. the circuit is
over-determined.

**Suggested fix.** Replace the example with one that genuinely has a fixed point — a reference to a
quantity the pump does not itself drive, e.g. `head=1.2*P1.dp` where `P1` is on a parallel branch whose
flow is set by a stated duty; or state the contraction condition explicitly (`|∂(k·dp)/∂H| < 1`) and
show `FS1405` firing on the closed-loop case as the *expected* outcome. Either way, recompute the table.

## F-29 · `01` · feasibility — the canonical circuit had no flow driver in its secondary loop 🔴

**Found while applying F-7**, not during the review pass, and it is the finding that mattered most.

**Finding.** The corrected cooling loop wired the pump on the **primary** leg (`N1 - PU1`, `PU1 - N2`).
The secondary loop is then `N2 → HE1 → 3WV → N2`, which contains no flow-driving component. Every
pressure drop around it is positive, so the only solution is **zero recirculation** — and with no
recirculation `N2` sits at the primary's 6 °C, so `HE1`'s stated `in=20` cannot be met at all.

**Why it blocked.** It is the M2 demo script and the reference every other worked example was to be
rebuilt on. `23-topology-and-graph`'s own `FS2214` ("nothing drives flow around this loop") is exactly
the check that catches it — which is a point in the check's favour, and the reason `FS2214` was raised
from info to warning while applying: its consequence is silent, and every temperature downstream of a
dead loop is wrong in a way that still looks like a solved circuit.

**Applied fix.** `PU1` moves into the secondary loop (`N2 - PU1`, `PU1 - HE1`). The circuit then
solves: primary 0.1629 kg/s at 6 °C mixes with 0.0764 kg/s of 50 °C recirculation to give 0.2394 kg/s
at 20 °C into `HE1`, which adds 30 kW to bring it to 50 °C. The primary-side energy balance closes
independently at 0.1629 × (h₅₀ − h₆) = 30 000 W, which is the check that the mixing fractions are right.
