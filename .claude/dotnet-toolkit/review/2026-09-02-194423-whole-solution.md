## Findings

### Core scope

#### `src/FluidScript.Core/Components/Pipe.cs:49`

- **Aspect:** `[correctness]`
- **Severity:** 🔴 Bug/must-fix
- **What:** The public constructor accepts non-finite geometry, including `double.NaN`, despite documenting positive/finite physical inputs.
- **Why:** Lines 58–62 use `ThrowIfNegativeOrZero`/`ThrowIfNegative`, whose runtime implementation checks only `IsNegative` and `IsZero`; neither rejects a normal NaN ([official runtime source](https://raw.githubusercontent.com/dotnet/runtime/main/src/libraries/System.Private.CoreLib/src/System/ArgumentOutOfRangeException.cs)). `length: double.NaN` or `insideDiameter: double.NaN` therefore reaches line 70, makes `FlowArea` NaN, and subsequently makes `EvaluateResiduals` return a NaN residual. `elevation` is not validated at all, so a non-finite elevation poisons the residual at line 162 as well. The eight test callers reported by `get_references` all pass ordinary finite values, and the test-method search found no NaN/non-finite case. `search_log` contained no recorded rationale for accepting non-finite geometry.
- **Fix:** Reject non-finite values before the existing domain checks (`double.IsFinite` for all geometry inputs), then retain the positive/non-negative constraints. Add theories covering NaN and both infinities for every constructor parameter that participates in the residual.

#### `src/FluidScript.Core/Components/Valve.cs:22`

- **Aspect:** `[correctness]`
- **Severity:** 🔴 Bug/must-fix
- **What:** Both valve constructors and their init-only `Position` properties allow values that violate their documented domain and can inject NaN into the solver.
- **Why:** `Valve` line 30 and `ThreeWayValve` line 135 only apply `ThrowIfNegativeOrZero` to `kv`, so `kv: double.NaN` survives. Lines 33/138 copy `position` without checking it, and the public init accessors at lines 67/180 let an object initializer replace it with any value after construction. A NaN position survives `Math.Clamp` in `ValveLaw.Opening`, so the calls at lines 97, 218, and 223 produce NaN residuals; finite out-of-range positions are silently clamped even though the public object still exposes the out-of-range value. Invalid `ValveCharacteristic` enum values are likewise accepted and silently treated as linear by `ValveLaw.Opening`'s default arm. `search_log` contained no recorded tradeoff for this behavior.
- **Fix:** Validate `kv` as finite and positive, validate `characteristic` with `Enum.IsDefined`, and make `Position` a validating init accessor that accepts only finite values in `[0, 1]`. Apply the same validation in both valve types and document the thrown exceptions.

#### `src/FluidScript.Core/Components/Valve.cs:91`

- **Aspect:** `[testing]`
- **Severity:** 🟡 Convention violation or needs verification
- **What:** The two- and three-way valve equation paths have no behavior-level test coverage.
- **Why:** With the workspace fully loaded, `get_references(direction: "callers")` returned `totalItems: 0` for both `Valve.EvaluateResiduals` at line 91 and `ThreeWayValve.EvaluateResiduals` at line 209. The same check found no construction sites for either public type. A test-index search found registry coverage for three-way-valve port metadata, but no valve residual/characteristic tests; `ValveLaw.Opening` and `ValveLaw.MassFlow` are called only by these untested production methods. Consequently, regressions in signed pressure-drop behavior, the three-way mass balance, complementary bypass opening, or the Kv conversion have no executable guard.
- **Fix:** Add focused component tests that directly construct both valve types and verify forward/reverse flow, two-port residual sign, three-way mass balance and complementary paths, characteristic endpoints, zero-drop regularization, and invalid constructor/property inputs.

### Shared test infrastructure scope

#### `tests/FluidScript.Fixtures/ScriptCorpus.cs:55`

- **Aspect:** `[docs]`
- **Severity:** 🔴 Bug/must-fix
- **What:** `MarkdownBlocks()` promises global file-then-line ordering and removal of the fence-supplied trailing newline, but the implementation processes `plan` before `docs` at line 68 and unconditionally appends `"\n"` at line 119.
- **Why:** Callers receive `plan/...` entries before lexically earlier `docs/...` entries and text ending in an added LF. This directly contradicts the API contract used by exact-text and deterministic-failure-name tests.
- **Fix:** Either implement the documented behavior by globally sorting blocks and not appending the closing-fence newline, or document the intended behavior precisely: `plan` then `docs`, with CRLF normalized and one trailing LF added.

#### `tests/FluidScript.Fixtures/ScriptCorpus.cs:244`

- **Aspect:** `[testing]`
- **Severity:** 🟡 Convention violation or needs verification
- **What:** The mutation generator cannot insert at end-of-file or into an empty buffer. The loop stops when `builder.Length == 0`, and line 246 chooses insertion positions with `Random.Next(builder.Length)`, excluding the valid insertion index `builder.Length`.
- **Why:** The method's stated purpose is to cover intermediate editor states, but common states such as typing after the final character or typing the first character into an emptied document are unreachable. The three current fuzz callers therefore share the same blind spot. No recorded rationale was found in `search_log`.
- **Fix:** Choose the mutation operation before applying the non-empty constraint. For insertion, use `random.Next(builder.Length + 1)` and allow it when the buffer is empty; restrict only deletion and replacement to non-empty buffers.
