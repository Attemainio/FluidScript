## Bugs / must-fix

### `src/FluidScript.Core/Syntax/Lexer.cs:425`

- **Aspect:** `[correctness]`
- **What:** An overflowing numeric literal is deliberately parsed as infinity, but the binder does not reliably reject it.
- **Why:** `ExpressionEvaluator.Number` wraps the value in `Quantity.FromSi`, and `BindingRun.Store` can publish it unchanged for a `let` binding or other untargeted value. `let x = 1e999` can therefore bind successfully as positive infinity and later contaminate arithmetic or component inputs. Existing exponent tests do not cover overflow/infinity, and the development log contains no decision accepting non-finite bound values.
- **Fix:** Detect `!double.IsFinite(token.Value)` during evaluation or binding, emit an error diagnostic, refuse to publish the value, and add bare-number, unit-bearing, and `let` overflow tests.

### `src/FluidScript.Core/Compatibility/ScriptCompatibility.cs:167`

- **Aspect:** `[correctness]`
- **What:** A contradictory-major diagnostic always uses `directives[1].Span`, which need not identify the directive introducing the contradiction.
- **Why:** For majors `[1, 1, 2]`, the diagnostic highlights the second `1`, not the later `2`. Current tests cover `[1,2]` and `[1,1]`, but not duplicate-before-conflict ordering or the exact span.
- **Fix:** Locate the first directive whose major differs from `directives[0].Major`, use that directive's span/value, and add a `[1,1,2]` span assertion.

### `src/FluidScript.Core/Compatibility/ScriptCompatibility.cs:263`

- **Aspect:** `[correctness]`
- **What:** Removing a leading BOM changes the scanned line's indices without adjusting its source offset.
- **Why:** `Lines` trims `\uFEFF` but yields the original `start`. An unsupported first-line version in a BOM-prefixed file receives a span shifted one character left. The existing BOM test uses a supported major and emits no diagnostic that would expose the offset error.
- **Fix:** Add one to the yielded first-line offset after trimming the BOM, or retain the original line and scan with a slice offset. Add an unsupported-major BOM test with an exact span assertion.

### `src/FluidScript.Core/Components/Pipe.cs:59`

- **Aspect:** `[correctness]`
- **What:** Constructor guards accept non-finite geometry and loss inputs.
- **Why:** `ThrowIfNegativeOrZero`/`ThrowIfNegative` do not reject `NaN`; positive infinity passes the current checks; elevation has no finiteness check. These values can propagate `NaN` or infinity into Newton residuals.
- **Fix:** Require `double.IsFinite` for all six numeric inputs before the existing positivity/range checks. Add `NaN` and both-infinity cases for each parameter.

### `src/FluidScript.Core/Components/Valve.cs:31`

- **Aspect:** `[correctness]`
- **What:** `Valve` accepts non-finite `kv`, non-finite/out-of-range `position`, and undefined `ValveCharacteristic` values.
- **Why:** Invalid values enter `ValveLaw.Opening`/`MassFlow` and can produce invalid openings or non-finite residuals instead of failing at the public boundary.
- **Fix:** Require finite positive `kv`, finite `position` in `[0,1]`, and `Enum.IsDefined(characteristic)`. Validate the init path too, document the exceptions, and add boundary tests.

### `src/FluidScript.Core/Cycles/VapourCompressionCycle.cs:154`

- **Aspect:** `[correctness]`
- **What:** Cycle entry points do not enforce the thermodynamic ordering their result contract assumes.
- **Why:** `Subcritical` accepts `condensingTemperature <= evaporatingTemperature`; `Transcritical` accepts a high-side pressure below the evaporating or critical pressure. `Compress` can then calculate negative/non-compression work and a `PressureRatio` that contradicts its documented above-one contract; the transcritical API can return a subcritical result.
- **Fix:** Require the resolved high-side pressure to exceed the low side, and require transcritical absolute pressure to exceed `refrigerant.CriticalPressure`. Reject non-finite inputs and add equal/inverted-boundary tests.

### `src/FluidScript.Core/Cycles/VapourCompressionCycle.cs:317`

- **Aspect:** `[correctness]`
- **What:** `Zones` converts every `SaturationEnthalpies` failure into a successful one-zone transcritical result.
- **Why:** Above-critical pressure and backend/state failures use the same failure result. A backend fault can therefore be silently reported as valid `ZoneShares(1, 0, 0)` with the original error discarded.
- **Fix:** Classify transcritical operation explicitly from pressure versus the critical pressure. Return one zone only for that case; otherwise propagate `saturation.Error`.

### `src/FluidScript.Core/Fluids/HumidAirSubstance.cs:160`

- **Aspect:** `[docs]`
- **What:** `AsFluidState` says non-zero humidity “is asserted rather than assumed,” but performs no such assertion.
- **Why:** It copies dry-air-basis enthalpy into `FluidState.Enthalpy`, whose contract is per kilogram of fluid. Current callers happen to pass zero humidity, but a future caller can silently introduce the basis error the remarks claim to prevent.
- **Fix:** Assert zero humidity before conversion, or eliminate the narrowing helper and construct a dry-air state only inside the two zero-humidity call paths. Make the remarks match the implementation.

### `src/FluidScript.Core/Fluids/Water.cs:160`

- **Aspect:** `[correctness]`
- **What:** Public substance methods ignore `Quantity.Dimension` and consume only `SiValue`.
- **Why:** A caller can pass a length as pressure, enthalpy as temperature, or a dimensionless value as entropy; Water, Refrigerant, and HumidAirSubstance reinterpret the number in the expected unit and may return plausible but physically meaningless states.
- **Fix:** Validate pressure, temperature, enthalpy, entropy, and humidity dimensions at every public boundary before calling the backend. Centralize the checks for consistent behavior.

### `src/FluidScript.Core/Fluids/Water.cs:216`

- **Aspect:** `[correctness]`
- **What:** Pressure/enthalpy and pressure/entropy paths call the backend before enforcing the known pressure portion of `ValidRange`.
- **Why:** `ISubstance.ValidRange` promises validation before every backend call. Out-of-range pressure can therefore produce `FS2004` instead of the specified `FS2003`. The same pattern occurs at `Refrigerant.cs:132`, `Refrigerant.cs:143`, and `HumidAirSubstance.cs:93`; comparison-only validation also lets `NaN` pass.
- **Fix:** Check the known absolute pressure and finiteness before the backend call, then validate the returned temperature afterward.

### `src/FluidScript.Core/Solvers/NewtonSettings.cs:35`

- **Aspect:** `[correctness]`
- **What:** `MinLineSearchStep` accepts negative and non-finite values; a negative value can make line search non-terminating.
- **Why:** `LineSearch` halves `alpha` until `alpha <= MinLineSearchStep`. With a negative minimum and no acceptable point, `alpha` underflows to zero, which remains greater than the negative threshold forever. Cancellation is checked only outside that loop. No invalid-settings test covers this.
- **Fix:** Validate solver settings: finite `MinLineSearchStep` in `(0,1]`, positive finite tolerances/divergence factor, and `MaxIterations > 0`. Independently cap line-search halvings as a defensive invariant.

### `src/FluidScript.Core/Solvers/NewtonSolver.cs:213`

- **Aspect:** `[correctness]`
- **What:** A stalled result reports the residual norm/diagnostic for the pre-step iterate while returning the post-step solution.
- **Why:** The solver updates `x`, then selects the worst row and formats/passes a norm from residuals evaluated before the update. `Stop` re-evaluates the returned `x` for `WorstResiduals` but keeps the caller-provided old norm, so one result describes two different iterates.
- **Fix:** Re-evaluate scaled residuals after the accepted step and derive the stalled norm, worst row, diagnostic, and returned result from the same evaluation.

### `tests/FluidScript.Api.Tests/HostCompositionTests.cs:26`

- **Why:** It checks only that source- and test-project roots exist. Any production subdirectory can lack its test counterpart while the named architecture invariant still passes.
- **Fix:** Enumerate relevant source directories, derive project-relative paths, and assert corresponding test directories exist, with explicit exclusions.

## Warnings

### `src/FluidScript.Core/Catalogs/Catalog.cs:161,180`

- **Aspect:** `[correctness]`
- **What:** `SmallestSatisfying` and `NearestBelow` index the first/last entry when an empty catalog selects no row.
- **Why:** Empty catalogs are a supported invalid state diagnosed by `Validate()`, yet these public methods throw `IndexOutOfRangeException`, contradicting the documented “Nothing here throws” behavior and bypassing the diagnostic path.
- **Fix:** Guard empty entries and return a modeled failure, or enforce successful validation during construction. Add empty-catalog selection tests.

### `src/FluidScript.Core/Components/Tank.cs:65-69,198-199`

- **Aspect:** `[correctness]`
- **What:** Tank construction accepts non-finite/out-of-range port elevations; `LayerFor` accepts elevations outside `[0,1]` and layer counts below one.
- **Why:** Invalid inputs can produce zero/negative layer indices or a zero result despite a documented one-based layer number.
- **Fix:** Require finite elevations in `[0,1]`, positive finite volume, and `layers >= 1`. Add boundary/non-finite tests.

### `src/FluidScript.Core/Components/Pump.cs:50-58,137`

- **Aspect:** `[correctness]`
- **What:** `speed` is unvalidated and remains an unrestricted init property; `efficiency` is checked only as positive.
- **Why:** Negative speed produces the same squared head as positive speed, excessive speed and efficiency above one are accepted, and `NaN` passes current guards. Invalid parameters can produce plausible-looking results.
- **Fix:** Require finite speed within the supported range and finite efficiency in `(0,1]`; prevent the init path from bypassing validation and add invalid-input tests.

### `src/FluidScript.Core/Components/HeatExchanger.cs:250-251`

- **Aspect:** `[correctness]`
- **What:** `ImpliedFlow` divides by unchecked `specificHeat * temperatureRise`.
- **Why:** Zero produces infinity, negative inputs return a negative flow “magnitude,” and non-finite inputs propagate invalid values.
- **Fix:** Require finite, strictly positive specific heat and temperature-rise magnitude, expose a documented failure mode, and test zero/negative/non-finite inputs.

### `src/FluidScript.Core/Components/PlacedSensor.cs:81`

- **Aspect:** `[correctness]`
- **What:** `MeasuredProperty => _kind.MeasuredProperty!` relies on a constructor-established invariant without retaining the validated non-null value.
- **Why:** A future constructor/factory change can invalidate the distant assumption while the suppression keeps compiling.
- **Fix:** Store `kind.MeasuredProperty ?? throw ...` in a non-nullable field and return it; at minimum, document the invariant beside the suppression.

### `src/FluidScript.Core/Components/Valve.cs` / `tests/FluidScript.Core.Tests/Components/ValveAndPumpTests.cs:103`

- **Aspect:** `[testing]`

### `src/FluidScript.Core/Fluids/HumidAirSubstance.cs:90`

- **Why:** Its only caller is the production zero-humidity adapter, leaving the basis-sensitive non-zero-humidity API without a round-trip or boundary test.
- **Fix:** Round-trip a non-zero-humidity state through `(p,T,w)` and `(p,h_dry,w)`, comparing temperature, humidity, and dry-air-basis enthalpy. Include invalid humidity and pressure cases.

### `src/FluidScript.Core/Fluids/HumidAirSubstance.cs:127`

### `tests/FluidScript.Core.Tests/Performance/BackendPairDiagnostics.cs:646`

- **Aspect:** `[concurrency]`
- **What:** Timing out a backend call abandons its thread without stopping the work.
- **Why:** `Invoke` returns after `thread.Join(CallTimeout)` fails, while the background thread continues indefinitely. Later candidates/calls proceed, so timed-out work can accumulate, consume CPU/native resources, and contaminate timing samples.
- **Fix:** Run timeout-prone probes in a killable child process, or use backend-supported cooperative cancellation and wait for confirmed completion before the next probe.
